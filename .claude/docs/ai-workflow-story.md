# AI 에이전트 워크플로우 설계 및 하네스 구축기

## 문제는 미용사를 찾는 것에서 시작됐다

머리를 자르러 갈 때마다 같은 고민을 반복했다. 네이버에서 미용실을 검색하면 상위에 뜨는 건 전부 광고였고, 실제로 내 취향에 맞는 미용사가 거기 있는지는 알 수 없었다. 미용실이 아니라 미용사를 먼저 찾고 싶었다. 내 두상에 맞게 잘라본 경험이 있는 사람, 내 지역 근처에 있는 사람, 리뷰가 좋은 사람. 그 세 가지가 전부였는데 그걸 한 번에 보여주는 서비스가 없었다.

그래서 **CutIng**을 만들었다. 광고 없이 위치·취향·예산 기반으로 미용사를 매칭하는 예약 앱이다. 미용사가 자신이 작업한 사진을 올리고, 베이지안 랭킹으로 광고 없는 신뢰 지표를 제공하고, 두상 사진을 올리면 AI가 어울리는 스타일을 추천해주는 구조다.

---

## 처음에는 AI를 그냥 썼다

프로젝트를 시작할 때 AI 활용 방식은 단순했다. 기능 설명을 입력하고 구현을 요청하는 것. 초반엔 빠르게 돌아가는 것처럼 보였다. 그런데 프로젝트 규모가 커지면서 같은 문제가 반복되기 시작했다.

**첫 번째 문제는 프론트엔드와 백엔드의 불일치였다.** 백엔드 API를 만들어달라고 하면 잘 만들어줬다. 프론트엔드 화면을 만들어달라고 해도 잘 만들어줬다. 그런데 둘을 연결하면 API 경로가 다르거나, 응답 형식이 다르거나, 화면에 연결이 아예 안 된 채로 끝나는 경우가 많았다. 기능 하나를 완성하는 데 계속 왔다갔다 해야 했다.

**두 번째 문제는 테스트 통과를 위해 로직을 바꾸는 것이었다.** 구현과 테스트를 함께 요청하면 AI가 테스트를 통과시키기 위해 기존 로직을 임의로 수정하는 경우가 생겼다. 테스트가 통과됐다고 해서 기능이 제대로 동작하는 게 아니었다.

**세 번째 문제는 컨텍스트가 길어질수록 일관성이 무너지는 것이었다.** 앞에서 정의한 엔티티 필드를 모르는 척 새로 만들거나, 이미 결정한 설계 방향과 다른 코드를 생성하거나, O(n²) 코드를 그대로 내놓는 일이 생겼다. 대화가 길어질수록 앞에서 정해둔 것들이 점점 희미해졌다.

## 1차 개선 : AI에게 역할을 주고 팀을 만들었다

원인을 생각해보니 AI를 그냥 혼자 쓰는 게 문제였다. 실제 개발팀이라면 설계자, 개발자, 테스터, 리뷰어가 따로 있고 각자 할 수 있는 것과 없는 것이 명확하다. 그 구조를 그대로 가져오기로 했다.

다섯 가지 에이전트를 만들었다.

- **planner-agent** : 코드를 읽고 구현 계획과 트레이드오프를 분석한다. 코드를 직접 수정할 수 없다.
- **backend-agent** : 반드시 격리된 브랜치(워크트리)에서만 작업하고, 빌드가 성공할 때까지 완료 보고를 할 수 없다.
- **frontend-agent** : 백엔드 에이전트 완료 후 API 연결과 화면을 구현한다.
- **test-agent** : 테스트 작성과 실행 전담이며, 구현 코드를 수정할 수 없다.
- **review-agent** : 보안, 성능, 컨벤션 위반을 검토한다. 코드를 고칠 수 없고 피드백만 줄 수 있다.

역할 분리와 함께 워크플로우 규칙도 네 가지로 정의했다.

1. **워크트리 격리 필수** : 모든 기능 구현은 메인 브랜치가 아닌 별도의 워크트리에서 시작한다. 실패해도 메인이 오염되지 않는다.
2. **계획 먼저, 승인 후 실행** : 코드를 수정하기 전에 변경 대상과 수정 방향을 텍스트로 먼저 작성하고 승인받는다. 구현 이후 되돌리는 비용을 줄이고 설계 단계에서 오류를 차단하기 위한 규칙이다.
3. **백엔드와 프론트엔드 동시 완성** : API 구현 후 반드시 화면 연결까지 완료해야 기능 완료로 인정한다. 실제 사용자 흐름 기준으로 기능을 검증하기 위한 규칙이다.
4. **테스트 및 리뷰 승인 후 병합** : 전체 테스트 통과와 리뷰 피드백 반영이 완료되기 전까지는 병합할 수 없다.

## 그런데 에이전트가 매번 같은 실수를 반복했다

팀 구조로 바꾸고 나서 큰 문제들은 사라졌다. 그런데 작은 실수가 계속 반복됐다. Jackson 패키지를 `com.fasterxml`로 import하거나(이 프로젝트는 Spring Boot 4.x라 `tools.jackson`을 써야 한다), `@Builder.Default`를 빠뜨리거나, Redis Stream에서 `@PostConstruct`에 `this`를 직접 전달해 순환 참조가 생기거나. 매번 실수하고, 고치고, 또 같은 실수를 반복했다.

에이전트가 이미 알고 있어야 할 것들을 모르는 게 아니라, **시작할 때마다 컨텍스트가 없는 게 문제**였다.

## 2차 개선 : AI가 먼저 읽어야 할 참조 문서를 만들었다

세 개의 문서를 만들었다.

- **architecture.md** : 기술 스택, 도메인 구조, API 경로, Redis 키 패턴. 에이전트가 코드를 탐색하기 전에 이 문서를 먼저 읽어 전체 구조를 파악한다.
- **conventions.md** : 일반 규칙, DB 규칙, Git 규칙, JPA 주의사항, 인증 패턴, 결제 플로우, 그리고 실수 목록. 에이전트가 반복한 실수들을 하나씩 여기에 기록했다. `com.fasterxml` 금지, `@Builder.Default` 필수, Kakao Maps `autoload=false` 필수 같은 것들이다.
- **workflow.md** : 에이전트 간 협업 순서, 완료 보고 형식, 빌드 검증 절차.

문서를 만들고 나서 같은 실수의 반복이 눈에 띄게 줄었다. 에이전트가 새 세션으로 시작해도 문서를 읽는 것만으로 프로젝트 컨텍스트를 복원할 수 있었다.

---

## 3차 개선 : 반복 패턴을 스킬로 정의했다

그런데도 남은 문제가 있었다. 기능 구현을 요청할 때마다 "설계 먼저 해줘 → 승인할게 → 그다음 구현해줘" 순서를 일일이 지시해야 했다. 한 번이라도 빠뜨리면 바로 구현부터 시작했다.

반복적으로 사용하는 작업 패턴을 스킬로 정의하고, 특정 상황이 감지되면 해당 스킬이 자동으로 활성화되도록 했다.

- **feature-implementation** : 기능 구현 요청 시 활성화. 설계 → 승인 → 구현 → 테스트 → 리뷰 순서를 강제한다.
- **bug-fix** : 오류 발생 시 활성화. 추측성 수정보다 원인 분석을 먼저 하도록 유도한다.
- **code-review** : 코드 리뷰 및 병합 가능 여부 검토 요청 시 활성화된다.
- **explain-code** : 코드 동작 방식이나 흐름 설명 요청 시 활성화. 도메인 맥락 중심으로 설명한다.
- **db-access-guard** : Repository 및 조회 로직 변경 시 활성화. N+1, 조회 성능, 트랜잭션 범위를 검토한다.

스킬이 적용되면서 지시 없이도 정해진 절차를 밟기 시작했다.

## 결과 : 무엇이 달라졌나

에이전트 팀 구성, 참조 문서, 스킬까지 세 단계의 개선을 거치고 나서 달라진 것들이 있다.

- 백엔드 API와 프론트엔드 연결 불일치 문제가 사라졌다. 프론트엔드 에이전트가 백엔드 완료 후에만 작업하고, API 스펙을 참조 문서에서 먼저 확인하기 때문이다.
- 테스트 통과를 위해 로직이 임의로 수정되는 문제가 사라졌다. 테스트 에이전트는 구현 코드를 수정할 수 없는 제약이 있어서다.
- 반복적인 import 오류나 어노테이션 누락이 크게 줄었다. conventions.md에 실수 목록이 쌓이면서 에이전트가 사전에 확인하게 됐다.
- 규모가 커져도 설계 방향이 유지됐다. 컨텍스트가 리셋돼도 참조 문서로 복원되기 때문이다.

---

## 남은 문제 : 회귀 버그

아직 해결되지 않은 문제가 있다. 새 기능을 추가하거나 기존 코드를 수정할 때, 그 변경이 다른 기능을 조용히 깨뜨리는 경우가 생긴다. 에이전트가 변경한 파일의 테스트는 통과하더라도, 연관된 다른 기능의 테스트를 돌리지 않으면 회귀 버그를 잡을 수 없다.

이 문제는 **자동화 회귀 테스트와 CI 파이프라인**으로 해결할 수 있다. 병합 전 전체 테스트를 자동으로 실행하고, 실패하면 병합을 차단하는 구조다. 규칙은 `workflow.md`에 정의했다.
